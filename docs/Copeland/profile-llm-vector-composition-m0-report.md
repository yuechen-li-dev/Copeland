# COPELAND-PROFILE-LLM-VECTOR-COMPOSITION-M0

**Outcome B: recognizable result, localized edits, but composition and filled-line
authoring still impose disproportionate friction.** The sketch succeeds as a
pressure test. It does not establish that the starting Profile API was
substantially easier than hand-written SVG for this illustration.

![Pelican riding a bicycle](../../samples/copeland-ts/profile-pelican-bicycle/pelican-bicycle.svg)

## Effort and approach

Approximately 10–15 minutes of sketch/source iteration, with additional time for
API inspection, the two small API additions, regression checks, and this report.
This is an estimate, not an instrumented timing benchmark. The first source was
created at 15:45 PDT on September 4, 2026; the color version and edit checks were
available around 15:56. One silhouette cleanup pass shortened the neck, moved the
eye away from overlapping geometry, narrowed the tail attachment, and opened a
bill seam. No feather or spoke polishing followed.

The approach was a side-view cut-paper illustration from memory: two rims, a
diamond frame, a seated oval body, leaning neck, round head, and a long hanging
pelican pouch. The near leg reaches the crank; the far leg is occluded. The wing
is represented by an oval negative space. There are no spokes or hands on the
handlebars. This is deliberately a simple cartoon pose.

Tools: repository inspection, ordinary Copeland/Profile compilation, .NET 10.0.400,
and Chrome headless screenshots for actual SVG inspection. No external image,
web search, tracing, image generation, or raster content was used. Python lacked
CairoSVG, so Chrome supplied the preview. Screenshots are inspection artifacts,
not the vector output.

## Starting capability inventory

Inventory authority: `ProfileTemplateFunctions.Source`, `ProfileTsxCompiler`,
`ProfileModel`, and `ProfileGeometry`, inspected before drawing.

| Capability | Starting qualification / limitation |
| --- | --- |
| Rectangle, RoundedRectangle | Available; rectangle-centered geometry; rounded corners lower to cubics |
| Circle, Ellipse | Available with explicit centers; curved contours generated by the compiler |
| RegularPolygon, Polygon | Available; Polygon accepts `number[][]` and closes the contour |
| Add | Available, but rejects intersecting **aggregate bounding boxes**, not merely intersecting contours |
| Subtract, Hole | Available under the existing contained-subtraction contract; not a general Boolean kernel |
| Tab, Notch | Available on an axis-aligned rectangle base |
| Translate, Rotate, Scale, Mirror | Available as whole-current-profile SSA operations; rotation is about the origin |
| RepeatRadial | Available for gear teeth on an untransformed Circle; not a generic spoke/shape repeater |
| Templates | Available through M1 typed specialization |
| Ordinary helper functions | Available, including typed records, conditionals, and explicit arguments |
| ProfileOperation[] | Available; no general immutable array spread in the qualified surface |
| Raw Path | **Absent**; Polygon is the available low-level escape |
| Cubic / quadratic / elliptical arc authoring | Canonical IR has cubic and quadratic segments, but TS/Profile has no authored curve-segment or arc primitive |
| Layered paint / style | No qualified source-level scene/layer composition or style record at the start |

Thus the drawing uses actual curves for circles, body, wing, and neck. It does
not approximate those with polygons. Beak and tail use polygons because no
authored curve API exists.

## Layout model and constraints

The source defines `Vec2`, `BicycleLayout`, and `PelicanLayout`. It uses direct
arithmetic, not a constraint solver. The compiled exporter derives scene bounds
from all layer bounds and adds 12 units of padding.

| Relationship | Encoded rule |
| --- | --- |
| Ground clearance | Rear-wheel center Y = WheelRadius + 12 |
| Wheelbase | Front center = rear center + (Wheelbase, 0) |
| Seat | Rear center + (0.33 × Wheelbase, 78) |
| Crank | Rear center + (0.60 × Wheelbase, 4) |
| Handlebar | Front center + (-16, 104) |
| Body | Seat + (0, BodyLift) |
| Head | Body + (65, 82) |
| Wing | Body + (-8, 4), radii controlled by WingScale |
| Knee and foot | Knee follows body; foot follows crank |
| Bill | Head-local polygon, controlled by BeakLength; rotates with head |

Increasing WheelRadius raises the wheel centers to maintain ground clearance.
All attached geometry moves with those anchors. Raising the body moves the head,
neck, tail, and knee while keeping the foot at the crank, changing leg extension.
These are deliberate dependency effects rather than unrelated coordinate edits.

## Layers, helpers, and source structure

Paint order is explicit in the evidence runner and the source's `BuildLayer`:

1. RearWheel, FrontWheel.
2. RearFrame, FrontFrame, Fork, Seat, Handlebar, Crank, CrankArm.
3. UpperLeg, LowerLeg, WebbedFoot.
4. Tail, Neck, BodyAndWing, Beak, HeadAndEye.

Legs are painted before the body to hide their attachment. Each layer has its
own ordinary Profile base, operations, named SSA states, and final `Finished`
yield. There is no combined intersecting-contour shape passed off as a union.

The 18 ordinary helpers include layout construction, `Offset`, `Tube`, both wheel
builders, both frame builders, `BuildPelicanBody`, `BuildPelicanHead`,
`BuildPelicanBeak`, `BuildPelicanWing`, `BuildPelicanTail`, `BuildPelicanLegs`,
`BuildLayer`, `FinishLayer`, and `BuildLayerStyle`.

No templates were needed. Two wheel helpers and the filled-segment helper were
sufficient repetition; `RepeatRadial` does not model generic spokes.

The source is still less direct than `BuildBicycle` / `BuildPelican` / `Compose`:
the runner selects the `Layer` constant 0–16 and compiles the same typed source
for each layer. Names and paint order are duplicated between that dispatch and
the runner. This is a real composition deficiency, not an idealized API demo.

## Small APIs added during this run

The user explicitly authorized implementing observed missing APIs after the
initial inventory. Two narrow changes were made:

- `ProfileSvgExporter.ExportLayers`: accepts named canonical `VectorShape`
  layers, preserves paint order and independent nonzero fills, derives padded
  bounds, and uses the existing contour-to-path implementation. It validates
  layer names and padding. The original unstyled one-profile SVG output remains
  byte-for-byte compatible with the existing tests.
- `ProfileStyle`: a typed record with `fill`, accepted by `<Profile style={...}>`
  through ordinary static record evaluation. The sample derives BicycleStyle
  and AccentStyle from InkStyle using **Copeland `with`**, not CSS. The bounded
  fill surface is `black`, `white`, or `#RRGGBB`; no CSS parser, gradients, masks,
  filters, opacity, or stroke semantics were added.

Styles are presentation data on the compilation result, separate from geometric
SSA. A color-only edit preserves Profile IR and canonical contour hashes and
changes SVG output. Unit tests prove this distinction. Layered export consumes
canonical contours directly; it neither edits previously exported SVG nor
reconstructs geometry from SVG text.

This is a static export API, not an illustration runtime or scene-graph engine.
The TSX frontend still accepts one Profile root. That remaining limitation is
visible in the benchmark source.

## Low-level escapes and friction

There are no raw SVG strings or authored raw paths in the semantic source.
There are eight localized Polygon construction sites:

| Feature | Workaround | Classification | Useful next helper |
| --- | --- | --- | --- |
| Frame tubes, fork, legs, seat, handlebars | `Tube` constructs a four-point filled polygon with Manhattan-normalized perpendicular offsets | B: geometry | Capsule/filled segment, then PolylineStroke |
| Rear and front frame | Two outer triangles and two inset triangular subtractions | B: geometry | PolylineStroke with predictable joins |
| Beak and seam | Head-local tapered pouch polygon and three-point negative seam | B: geometry | Closed curve path or tapered shape |
| Tail | Four body-relative polygon points | E: drawing effort | No new language feature needed |
| Overlapping body/neck/head/frame | Separate canonical Profile layers | C/D: composition/export | ExportLayers implemented; typed source-level layer list still missing |
| Initial color output | Record style and `with` values | D: export | ProfileStyle implemented |
| Constants referenced inside helpers | `COPE-BIND-0001: Undefined name 'WheelRadius'` and similar diagnostics | A: language/capture contract | Explicit helper arguments solved it; no language change needed |
| Rotation around head | Head-local construction followed by Rotate and Translate | C: composition | Pivot/attach convenience could remove repeated plumbing |
| Empty finish branch | Identity Translate gives all layers a common named yield | C: composition | Scene/layer API should avoid this common-yield workaround |
| Wing enlargement | Bigger negative ellipse exposes a small neck intrusion near its upper-right edge | E/C: drawing/paint composition | A separately painted wing could avoid the transparent-cutout interaction |

The polygon `Tube` width is approximate, and its ends are square. The frame has
a small antialias seam between adjacent independently exported triangles.
Neither prevents recognition. No claim of anatomical or stroke-join fidelity
is made. These were deliberately left after the single cleanup pass.

Scene Profile and contour hashes are SHA-256 of newline-joined constituent
hashes in paint order. They are explicitly **aggregate hashes**, not the hash of
a fictional Boolean-unioned scene contour. Full scene SVG bytes have their own
SHA-256. Style is intentionally absent from geometric hashes.

Counts are lexical, not AST complexity metrics. Source numeric counts also
include layer indices and ordinary layout constants. Polygon counts count
literal occurrences, not named coordinate expressions. Export coordinate counts
use only `d` attributes, excluding colors, IDs, and the viewBox.

The semantic source compresses **intent and edits**, but is not shorter than
competent SVG using native circles/ellipses, groups, and strokes. The exported
canonical-path SVG is a lower-level comparison target than all of SVG. No
separate raw-SVG recreation or timed A/B experiment was performed.

## LLM authoring assessment

1. **Substantially easier overall?** Not established. Parameters and typed
   decomposition helped, but the initial API blocked overlapping composition.
2. **Dramatically easier parts?** Repeated circles, contained holes, relative
   anchor propagation, and the four requested edits.
3. **Still coordinate work?** Tube thickness, triangle insets, bill pouch, tail,
   and arranging the neck relative to the wing cutout.
4. **Did records help?** Yes. Wheel-size and body-height changes propagate along
   legible relationships instead of requiring coordinate searches.
5. **Did layering help?** Yes. It allowed a recognizable pose without solving
   Boolean unions or tracing a giant connected outline.
6. **Did TSX improve visibility?** Modestly for each layer's base/operations/yield;
   poorly for the full scene, which still needs external layer selection.
7. **Were ordinary helpers natural?** Yes after making captures explicit.
   Helper names needed no special TSX registration.
8. **Were escapes localized?** Yes: eight Polygon sites, one reusable Tube
   helper, no SVG path blob. Localized does not mean effortless.
9. **Highest-impact next feature?** A typed source-level layer composition API
   over the now-existing exporter, removing numeric dispatch and identity
   finish operations. PolylineStroke is the next geometry candidate after that.
10. **Could a fresh model edit it?** Likely for the five obvious parameters and
    palette records; less confidently for adding a new layer because dispatch
    and ordering are split across TS and C#. This is an assessment, not a
    fresh-model user study.

## Validation and scope

Reproduce from repository root:

```powershell
dotnet run --project tools/Copeland.Profile.VectorCompositionM0Evidence -c Release
dotnet test tests/Copeland/Copeland.TS.Tests/Copeland.TS.Tests.csproj -c Release
dotnet test tests/Machina.UI/Machina.Fonts.Tests/Machina.Fonts.Tests.csproj -c Release --filter 'FullyQualifiedName~ProfileVectorIconCompilerM0Tests|FullyQualifiedName~VectorIconCompilerM5Tests'
```

- All 85 layer/variant combinations compile twice: 170 successful compilations.
- Repeated Profile IR, canonical contour, individual SVG, and scene SVG hashes
  match. Every selected layer resolves; expected edit dependency changes pass.
- Every canonical segment joins the next exactly, including contour closure;
  coordinates are finite under VectorPoint/VectorShape construction. Compiler
  diagnostics are empty and SVG export succeeds. Visual inspection found no
  broken contours. This is not an independent general self-intersection proof.
- No runtime TSX, JSX tree, or illustration interpreter is emitted: Profile
  source goes through the existing static-value materializer and returns
  canonical Profile results directly. The evidence runner rejects `<svg` and
  `<path` in the semantic source.
- The requested M0/M1/M2 focused regression lane passed **33 tests**. Adding the
  initial layer-export tests brought that focused run to **36**.
- After style support, the full Copeland suite passed **1,224 tests**, including
  all three requested milestones and six new layer/style test cases. The full
  suite was justified by changes to the shared Profile expression host/module.
- Relevant Machina Profile/vector MSDF regression coverage passed **21 tests**
  against the final shared implementation. Existing third-party font field
  warnings appeared on its first build; there were no test failures.
- No optional pelican MSDF/native export was attempted. Independent paint
  layers, colors, and overlapping shapes are not one qualified MSDF field.
  No Vulkan, shader, atlas, renderer, Machina.Canvas, or other repository changed.
