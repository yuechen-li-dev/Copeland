# Copeland TS semantic ownership

> Parsing may vary by source frontend. Canonical meaning must not.

> Generated artifacts transport compiler meaning. They do not redefine it.

This map is the ownership rule for new work. A downstream layer may project,
transport, materialize, inspect, or realize a fact. It must not independently
infer that fact from source, tokens, DOM, or a different representation.

## Dependency direction

```text
Syntax/frontends
  -> binding and type checking
    -> bound nodes / Cope MIR / normalized domain models
      -> backends, artifacts, CLI/LSP projections
        -> TSPack materialization and browser runtime
          -> renderer adapters
            -> application bootstrap and samples
```

Forbidden reverse directions include semantic nodes depending on TSPack,
binding depending on a browser runtime, generic document meaning depending on
Machina layout, CLI table schemas defining compiler semantics, and renderer
adapters assigning component identity.

## Authorities

| Semantic concept | Intended authority | Valid projections/consumers | Must not own it |
| --- | --- | --- | --- |
| Tokens, grammar, recovery | `Syntax/Lexer.cs`, `Parser.cs`, syntax nodes | VS Code grammar, diagnostics | LSP token reconstruction |
| Symbols, types, validation | `Semantics/Binder.cs`, `Symbols.cs`, `Types.cs` | MIR/backends/LSP | JS/C# emitters, CLI |
| Source/module/package graph | `CopelandProjectContext` + TSPack resolved descriptor | CLI/LSP/build | ad-hoc source scans after manifest resolution |
| Records/enums/results/control flow | bound nodes then Cope MIR | C#/JS emitters | backend-local type rules |
| Layout box identity and normalization | Machina layout binding/compiler | CSS, inspection tables, host selectors | DOM/CSS/sample code |
| Document meaning | `DocumentMir` / text document binding | text tables, renderers | Markdown/DOM renderers |
| Component definition/instance identity | binder and `BoundComponentInstance` | frames, attachments, LSP, tables | renderer adapters, browser DOM |
| Component application state | component frame | presentation and adapter deltas | adapters or component payloads |
| Renderer compatibility/capabilities | adapter contract + bound attachment planning | attachment artifact, diagnostics | TSPack inference |
| Attachment identity and host box | `HostAttachmentMir` | `attachments.json`, runtime record | React root/DOM node |
| Attachment transport | `attachments.json` v1 | TSPack validation/loader | handwritten app registration |
| Browser materialization/lifecycle | `@copeland/browser-v1`, generated by TSPack | adapters/app bootstrap | compiler binder |
| Concrete host node and adapter root | browser runtime / adapter | runtime inspection only | compiler artifacts |
| Projected relation schema | CLI provider over bound facts | JSON/table display | formatter/source reconstruction |
| LSP diagnostics/hover | shared project snapshot and bound facts | VS Code UI | independent semantic engine |

## Browser runtime topology

```text
Copeland compiler -- HostAttachmentMir --> attachments.json (v1)
                  -- frame contracts ----> component-frames.js
                                      |
TSPack validates/materializes unchanged facts and generates bootstrap
                                      |
@copeland/browser-v1 (TSPack Go source -> generated JS)
  semantic-host readiness/recovery | attachment registry | frame registry
  lifecycle/cleanup/diagnostics    | renderer adapter registry
                                      |
Custom Element adapter         application-owned React bootstrap
                                      |
Concrete DOM nodes and opaque adapter roots
```

The present source of truth for the browser runtime is the `browserHostModule`
in sibling TSPack's `cmd/tspack/browser_materialization.go`, not emitted `dist/`
output and not Copeland sample `runtime/browser-v1.js` files. Those sample
files remain compatibility/runtime-contract inputs for individual historical
fixtures; they are not the attachment/frame runtime authority. TSPack's
generated module replaces the `@copeland/browser-v1` materialization for a
browser build.

This arrangement is acceptable for M0 because it produces deterministic,
versioned materialization and TSPack already owns browser bootstrap. Its cost
is a large Go string with JavaScript behavior. The recommended M1 is to extract
that string into one checked-in, independently tested JavaScript/TypeScript
runtime source owned by TSPack, retaining Go only as a thin copier/configurer.
That is a TSPack change, not a Copeland compiler refactor.
