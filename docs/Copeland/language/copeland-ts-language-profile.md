# Copeland TS language profile

**Status:** canonical product-language profile (CTS-M0a through CTS-M4c). CTS-M0d ratifies the accepted CTS-M0c core-semantic decisions and adds narrow frontend enforcement; CTS-M1 adds strict-mode JavaScript emission, CTS-M2 implements primitive equality, CTS-M3 implements private nominal payload-enum construction plus exhaustive match in that backend, CTS-M4b implements first-class Result source/MIR semantics, and CTS-M4c implements the same Result slice in JavaScript with bounded C#/Node parity evidence. Postfix unwrap and lexical handlers remain unimplemented. This document supersedes the current-tense language claims in historical milestone records and the support matrix.

## Position

> Copeland TS is intended to be a TypeScript-shaped, closed-world language that preserves TypeScript’s authoring ergonomics without inheriting JavaScript’s dynamic runtime semantics.

“TypeScript-shaped” means that TypeScript 7 is the intended syntax and ecosystem reference point, not a promise of full TypeScript 7, JavaScript, npm, DOM, or arbitrary JavaScript-interop compatibility. Copeland TS owns its runtime meaning. JavaScript is the planned first usable distribution/reference backend; the C# backend is currently a proof backend and the later .NET direction is RyuJIT for ordinary managed execution, NativeAOT for supported native deployment, and .NET WebAssembly AOT for browser/Wasm.

## Reading this profile

The status vocabulary is deliberate: **Normative direction**, **Implemented**, **Partially implemented**, **Intended, unimplemented**, **Historical experiment**, **Rejected**, and **Unresolved**. “Implemented” requires current production code and tests; an artifact emitted by the C# proof backend does not establish a language law. CTS-M0b adds curated source-level fixture evidence under `tests/Copeland/Copeland.TS.Tests/Language`; those fixtures establish frontend-to-MIR acceptance or normal validation rejection without loading a backend. [CTS-M0c core semantics and JavaScript-lowering design](copeland-ts-core-semantics-cts-m0c.md) remains the historical decision record; [CTS-M0d](../../migrations/cts-m0d-accepted-core-semantic-enforcement.md) accepts its selected recommendations as doctrine. [CTS-M4a first-class Result design](copeland-ts-first-class-result-design-cts-m4a.md) records the accepted laws separately from its unimplemented MIR recommendation. Normative direction does not imply current syntax, MIR, runtime, or backend support.

## Current implementation boundary

The implemented path is source text -> syntax -> binder -> Cope MIR -> deterministic `.cope` text, C# proof emission, or the nonfallible JavaScript backend. The CLI accepts `compile <source> --emit mir|csharp|javascript`. CTS-M2 proves Boolean, binary64 (including NaN and signed zero), and string equality through source-to-MIR-to-strict-JavaScript-to-Node execution. CTS-M3 proves private nominal payload-enum construction, payload order, exhaustive match, nested enum/match values, and corruption panic through the same JavaScript/Node route. It does not prove browser compatibility, interop, arrays, fallibility, Result, objects, or classes. `.cope` is an expected textual projection of MIR, not source input or a parser contract. The C# backend remains implementation evidence rather than authority for JavaScript semantics.

## Explicit exclusions and planned work

Current exclusions include `var`, `===`, `!==`, `eval`, `null`, ordinary object literals/member access, ternary `?:`, optional chaining `?.`, and implicit global assignment. The language direction also excludes truthiness, implicit coercion, `any`, ordinary `undefined`, ambient nullability, prototype behavior, and implicit host access. Payload enums and explicit fallibility are the intended native alternatives for tagged alternatives and failure; they do not yet settle all optionality or error-construction details.

## Unresolved decision surface

CTS-M0d accepts binary64, typed `==`/`!=`, rejected strict equality spellings, deterministic evaluation order, private payload-enum representation direction, Result-flow laws, and ordinary-enum optionality as language law. CTS-M3 now supplies JavaScript evidence for private nominal payload-enum construction and exhaustive match, while keeping the physical record layout private. `unknown`; canonical optional spelling; class/object identity and inheritance; array mutation/bounds/equality; closures; modules; panic ABI; first-class Result/fallibility emission; and explicit JavaScript interop syntax remain unresolved or deferred. These are decisions, not TODOs for a backend to choose opportunistically.

## CTS-M0b fixture contract

`TestData/Corpus` remains compiler-regression and generated-artifact evidence. `Language` is curated language-law evidence:

```text
tests/Copeland/Copeland.TS.Tests/Language/
  Valid/<semantic-area>/*.cl-valid.ts
  Invalid/<semantic-area>/*.cl-invalid.ts
```

- A valid fixture must parse, bind, validate, and lower to Cope MIR without diagnostics.
- An invalid fixture must be rejected by the intended language-validation stage. A crash, parser accident, backend failure, or unrelated diagnostic is not a correct rejection.
- Add exact diagnostic expectations only when diagnostic identity is itself contractual; add runtime companions only for observable execution semantics.
- No test DSL is needed merely to classify a source file as valid or invalid.

CTS-M0d contains 9 valid and 16 invalid fixtures. `var` now parses as an ordinary declaration and is rejected by `COPE-PROFILE-0001`; strict equality spellings parse and are rejected by `COPE-PROFILE-0009`. Explicit optionality remains unresolved: payload-enum fixtures establish tagged-data behavior, not a canonical `Option` representation or any JavaScript representation.
